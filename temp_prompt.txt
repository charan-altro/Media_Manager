## Root Cause Analysis — Two Separate Issues

### Issue 1: Seeking NOT triggering for episodes (all `at 0s`)

**The seeking mechanism depends entirely on `duration > 0`** in the player. Trace the dependency chain:

```
ep.duration_secs → activeDuration → VidstackPlayer `duration` prop
                                              ↓
                              isPiped && duration > 0 → duration override on <video>
                                              ↓
                              Vidstack knows video length → scrubber enabled
                                              ↓
                              handleSeeking fires → onSeek(targetTime) → setStartOffset
                                              ↓
                              sources recomputed → URL appended with ?start=XXX
```

**The break point**: At line 702 in `DetailModal.tsx`, `duration: ep.duration_secs || 0` — if `ep.duration_secs` is `null` or `0` in the DB for episodes, the entire seek chain breaks.

**Why movie_6 works**: `movie_6` has a non-zero `duration_secs` stored in `movie_files`, so seeking triggers correctly. Episodes that fail likely have `duration_secs = 0` or `NULL` in the `episodes` table — they were never scanned/updated with this value.

**Verify**: In `handleSeeking` (line 508), there's this guard:
```js
if (Math.abs(targetTime - startOffset) < 2.0) return; // Prevents seek when duration=0
```
With `duration=0`, the `<video>` element has `duration=Infinity` (piped stream), the scrubber is disabled entirely, so `handleSeeking` never fires, and `onSeek` is never called → backend always gets `start=0`.

---

### Issue 2: libopus `-22 Invalid argument` error (even with subtitle fix)

Error is now `[aost#0:1/libopus]` — the **audio encoder** failing on Matroska pipe. This is a **separate FFmpeg bug** with libopus + matroska + pipe:1 + `-ss` seeking. When FFmpeg seeks before input and encounters the audio encoder writing to a pipe, certain timestamp edge cases cause invalid packets. **This error is benign when seeking works** (the old process is killed, new one starts at the right position), but you're seeing it cascade because:

1. Episode duration is `0` → seek never sends a timestamp → FFmpeg restarts always at `0s`
2. The browser keeps requesting `0s` repeatedly (network error/retry loop from the pipe closing prematurely)

**The fix needed**: Ensure `duration_secs` is populated in the `episodes` table for all episodes by running a rescan or triggering an ffprobe on them from the scan pipeline.

**To confirm**: Check the DB directly — run a query like:
```sql
SELECT id, title, duration_secs FROM episodes WHERE duration_secs IS NULL OR duration_secs = 0 LIMIT 20;
```

The episodes with `duration_secs = 0` or `NULL` are exactly the ones that won't seek.
